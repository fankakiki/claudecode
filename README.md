# sjtu_grab — 选课回流票监控（接口版）

直接重放后端接口，不开浏览器。单轮耗时约 **几十毫秒**，而 Selenium 方案是 2~5 秒 ——
回流票的窗口期常常不到 1 秒，这个差距比其他所有优化加起来都重要。

```
pip install requests
```

## 三步上手

### 1. 抓查询接口

选课页面 → `F12` → **Network** → 勾上 `Fetch/XHR` → 正常点一次「查询」。
找到那条返回课程列表 JSON 的请求（点 Response 能看到课程名的那条），
右键 → **Copy** → **Copy as cURL (bash)** → 存成 `query.curl`。

> Windows 上不要选 "Copy as cURL (cmd)"，格式不同解析不了。

### 2. 抓提交接口

在**目标课程**（此刻是满员的）上点一次「选课」，让它失败。
把这条提交请求同样 Copy as cURL (bash) → 存成 `submit.curl`。

这一步是整个方案的关键：因为抓的就是目标课程自己的提交请求，
请求体里的教学班号/课程号已经是对的，脚本原样重放即可，
**不需要理解学校接口的任何字段含义**。

### 3. 先探测，再开跑

```bash
python sjtu_grab.py probe --keyword MARX6007
```

probe 会打印匹配到的课程记录、余量是怎么算出来的、提交请求长什么样。
**确认余量数字和页面上显示的一致**，再开始：

```bash
python sjtu_grab.py run --keyword MARX6007
```

先用 `--watch-only` 跑几分钟验证读数稳定，是很划算的一步。

## 常用参数

| 参数 | 说明 |
|---|---|
| `--interval 1.0` | 轮询间隔秒 |
| `--burst 3` | 命中余量后连续提交次数（失败立刻重试，不等下一轮） |
| `--workers 2` | 并发提交线程数，默认 1 |
| `--watch-only` | 只监控不提交，用来验证配置 |
| `--start-at 12:30` | 定时开抢，到点前静默等待 |
| `--keep-going` | 抢到后不退出（默认成功即停） |
| `-v` | 打印每轮实际耗时 |

字段推导不准、或结果判定不对时，复制 `config.example.json` 为 `config.json` 再调整。

## 排障

| 现象 | 原因 / 处理 |
|---|---|
| `登录态失效` | Cookie 过期了，重新抓一次 `query.curl` |
| `连续 N 轮没找到 XXX` | 抓的接口带了分页/筛选参数，目标课不在返回结果里。换一条 XHR，或在抓包前先把课程筛出来再复制 |
| `无法识别余量字段` | 照 probe 打印的字段名，在 `config.json` 里填 `remaining_field` 或 `capacity_field`+`selected_field` |
| 余量算反了（满员显示 180） | 配置里把 `combo_order` 改成 `capacity/selected`，或显式指定字段 |
| `HTTP 429` 频繁 | 被限流了，**调大** `interval`。打得太猛反而彻底抢不到 |
| 提交总是"未成功"但其实成了 | 把真实响应贴出来，按它改 `success_pattern` / `fail_pattern` |

## 几点说明

- 脚本只会重放你提供的那条提交请求，**永远不会调用退选接口**。
- 结果判定是"先判失败再判成功"。很多系统失败响应里也带 `"code":"1"`，
  只看 code 会把失败当成功。
- 默认间隔 1 秒已经比人工快两个数量级。不要调到几十毫秒去打学校的服务器：
  容易触发风控，而且是给别人添麻烦。遇到 429/5xx 脚本会自动指数退避。
- 抢到后日志会提示你去系统里刷新确认 —— 以系统页面为准，不要只信日志。
